# 当前模式：代码审查

## 职责
- 仅审查代码，**不修改任何代码**
- 审查意见统一放到 `review/` 目录下，按日期命名：`review/review_YYYY-MM-DD.md`
- 如已有当天审查文件，则追加内容

## 审查 Checklist

研发提交审查前，请确保完成以下检查项：

### 功能正确性
- [ ] 是否符合 PRD / 需求文档
- [ ] 边界条件和异常场景是否覆盖
- [ ] 是否存在潜在的死循环、资源泄漏、并发问题
- [ ] 改动是否有完整的单元测试覆盖

### 代码质量
- [ ] 代码是否符合项目已有风格和约定
- [ ] 是否存在重复代码或过度设计
- [ ] 命名是否清晰自文档化
- [ ] 函数/方法职责是否单一
- [ ] 是否存在魔法数字、过长函数、过深嵌套

### 安全性
- [ ] 输入是否经过校验和转义
- [ ] 是否存在 SQL 注入、XSS、CSRF 等安全风险
- [ ] 敏感信息（密钥、Token）是否未硬编码
- [ ] 权限校验是否到位

### 性能
- [ ] 是否存在不必要的重复计算或查询
- [ ] 是否有 N+1 查询等性能隐患
- [ ] 大数据量场景是否有分页或批量处理

### 可维护性
- [ ] 是否添加了必要的注释（复杂逻辑、Why 而非 What）
- [ ] 日志是否合理（级别正确、信息有足够上下文）
- [ ] 是否更新了相关文档或 API 定义

---

## 审查流程
1. 研发提交审查请求时，附上 Checklist 完成情况
2. Reviewer 逐项审查代码，记录问题到 `review/` 目录
3. 研发根据审查意见修改后，在 `review/` 文件中逐条标记修复情况
4. Reviewer 复查，确认关闭所有问题后合并
